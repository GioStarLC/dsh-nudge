# 发版流程

把散乱的工作区改动变成一次可推送的发布。产物有三样：一组按主题的提交、一份人能读懂的版本说明、一个带 tag 的推送。

`CHANGELOG.md` 是生成物，不要手工编辑。要改某一版的措辞，改 `scripts/release-notes/<tag>.md`，然后重新生成。

## 1. 先确认三个事实

```sh
git tag --sort=-creatordate | head -3     # 上一版叫什么
git log --oneline origin/main..HEAD       # 已提交但没推的
git status --short                        # 工作区还有什么没提交
```

"上次推送"和"上次发布"不是一回事。版本边界以**最近的 tag** 为准，`origin/main..HEAD` 只说明哪些提交还没上远程。

工作区有未提交改动时先看清楚是什么，再决定并入哪次提交。不要 `git add -A` 一把梭，容易把半成品带进去。

## 2. 拆提交：一条提交一件事

提交信息按 Conventional Commits 写，标题会自动归入更新日志的分类：

```
feat(scope): 用户视角的一句话
fix(scope): ...
test: / docs: / build: / chore:
```

正文里以 `- ` 开头的行会成为该条的子条目，其余正文不进日志，可以放心写"为什么这么改"。

拆分依据是**用户能感知的变化**，不是文件。一个文件里改了四件事就该四条提交；跨三个文件做一件事就一条提交。一条提交塞六件事，正文只能写成并列清单，清单必然技术腔。

拆不开时（同一文件里改动交织、中间态跑不过校验）宁可少量粗提交，也不要拆出一堆跑不起来的中间态。

## 3. 写版本说明

版本说明单独写，不要复用提交正文。提交正文的读者是下一个改这块代码的人，版本说明的读者是装了这个插件的人。两种视角混用，必然写出技术腔。

放在 `scripts/release-notes/<tag>.md`，只写正文（从 `### 新增` 这类小标题开始），标题和日期由脚本生成。

写法：

- 一条一句，写完断行。不在句子里接"因为…""这样做的意思是…"。
- 用「以前怎样，现在怎样」当骨架，但只留半句对比，不解释原因。
- 只写用户能感知的差异。防抖毫秒数、白名单、载荷上限、HTTP 状态码、接口路径、环境变量，全部留在提交正文里。
- 按"用户会遇到什么"分组，不按代码模块分组。
- 术语跟界面上的字样一致（悬浮窗、批注、快捷问法），不自创新词。
- 宁可少写。能删的条目就删。

反例 → 正例：

| 技术腔（提交正文可以这么写，日志不行） | 人话 |
| --- | --- |
| 设置快照按 300ms 防抖同步到 Host，本地存储被清空时回灌 | 设置会记住了：重启或换了端口，问法、开关、位置都不再回到默认 |
| 只接受白名单键与预期结构，载荷上限 256KB，写入临时文件加改名 | 删掉，用户无感 |
| 悬浮窗底部那行小字 | 悬浮窗标题栏下面那行小字 |

位置、方向、按钮名称这类词去界面代码里核对一次，不要从旧文档或记忆里搬。位置写错比写技术细节更伤。

## 4. 生成、发版、打 tag

```sh
node scripts/changelog.mjs --write --version vX.Y.Z
git add -A && git commit -m "chore(release): vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z — 一句话概括"
```

版本号：修 bug 升 patch，新功能升 minor，破坏性改动升 major。

## 5. 校验：生成必须幂等

```sh
node scripts/changelog.mjs --write && git status --short CHANGELOG.md   # 应当无输出
npm run check
```

第一条无输出，说明标签里的 CHANGELOG 就是这个版本最终的样子。做不到幂等，通常是因为有人直接改了 `CHANGELOG.md`，把内容挪回 `release-notes/` 即可。

## 6. 推送

```sh
git push --follow-tags
```

`--follow-tags` 会把注记 tag 一起推。推送前确认版本说明的措辞已经定稿，推上去再改就要动历史。

## 坑

- **tag 还没推时一切都可重来**：`git reset --soft HEAD~1` 改发版提交，`git tag -d vX.Y.Z` 重打。
- **`--version` 撞已有 tag 会直接报错**，这是故意的：已发布的段落只由标签决定，不接受重命名。
- **打 tag 前后生成的字节必须一致**，靠两条不变量：发布块按最新一条真实提交的日期命名（不是 tag 创建时间）；`chore(release):` 这类提交自身不进日志。
- **工作区脏时脚本会警告并列出文件**，这些改动不在任何区间内。看到警告先提交。
- **git 对象损坏会一路传导**：`git push` 报 `unable to read <hash>` 或 `index-pack failed`，先 `git fsck` 定位。若损坏对象在新的可达图里、而内容还在磁盘上，用 `git reset --mixed <baseline>` 从干净基线重做提交（`--soft` 会保留指向坏对象的索引条目，坏 blob 被反复复用）。彻底修复：从远程重新 clone 一份，把 `.git` 换进来，再 `git config core.autocrlf true && git add --renormalize .`。
